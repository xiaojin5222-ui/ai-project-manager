# AI 项目管家

让需求、实施与验收对得上。重要工作先确认完整计划，再在已批准范围内持续实现、测试和修正；用实际证据说明结果。

## 1. 选对流程

- **完整流程**：新项目、重要功能、跨模块变更，或涉及权限、数据结构、外部系统等实质风险。按下文先形成计划，再实施。
- **轻量流程**：目标明确、局部、可逆且低风险的修改。用几句话说明改动与检查方法，直接完成授权范围内的修改和必要验证，无须完整模板或新增审批。修改行数少不代表风险低。
- 已有对同一具体范围、实施方案和验收标准的明确批准时，沿用该批准，简述执行依据，不重复问已回答的问题。“做一个系统”等宽泛意向本身不等于具体计划已批准。
- 用户当前明确的流程指令优先于本技能。遵守宿主权限和适用项目指令；技能只提供工作方法，不扩大任务授权。

## 2. 先形成一个可批准的计划

在改变项目代码、配置或依赖前，只读查看与任务相关的项目说明、适用指令、当前实现、测试和工作区改动。避免读取无关私密文件或收集凭据。

明确业务目标、使用者、现状、范围内与范围外、约束、关键假设、实现方案和可观察的验收条件。先利用已有上下文；只集中询问会改变方案、风险或验收的未知事项。低影响且可逆的选择可注明假设后推进；不能安全推断的关键条件须等回答。

提交一份连贯计划供人确认，包含：

1. 用户完成什么任务，怎样算成功。
2. 做什么、不做什么，以及关键约束和取舍。
3. 最小完整业务流程，随后按业务可验证的结果划分里程碑。
4. 每个里程碑的实现步骤、验收方法、证据，以及主要风险和恢复办法。

正常流程之外，按实际相关性考虑无效输入、重复操作、取消、失败、重试与恢复。说明哪些不适用及理由即可，不为凑齐清单添加功能。

需要结构化表达时，读取 [紧凑模板](references/templates.md)，按需使用对应部分。方案可直接写在对话中；不强制创建文档体系。尚无具体批准时，在这份完整计划后等待批准，不提前实现。

## 3. 批准后持续推进

记录获批范围和验收依据，先完成最小业务闭环。每个里程碑都要有用户能观察的结果，不仅是“完成接口”或“写了文件”。在范围内自行处理实现细节、修复相关问题并运行适当检查；不要把每个小任务都变成新的审批。

保留用户改动，遵循现有架构与项目约定，只修改完成任务需要的内容。使用项目现有的版本或检查点方式；必要时先区分已有改动和本次改动，再留下可追踪的差异。提交、分支等操作依照已有授权和项目规则，不自动推送或部署，不用破坏性重置覆盖用户成果。代码回退不等于数据回退；涉及数据变化时须单独明确影响、恢复能力和授权。

出现实质范围、验收、成本或风险变化，或宿主要求额外权限时，暂停受影响步骤。说明发现、影响、可选方案和建议；取得必要确认后再继续，无关且安全的已授权工作可继续。不要悄悄扩大范围，也不要默默降低验收标准。

本技能不授权发布、部署、生产变更、凭据访问或处理、破坏性操作、付费行为及对外发送或上传。计划批准不替代这些动作所需的明确授权和宿主许可。不绕过权限拒绝；结果不确定时先核查，不盲目重试有副作用的操作。受阻时写清动作、目标、原因、已完成部分，以及被拒绝、待处理或结果不确定的状态。

## 4. 用证据验收

检查计划是否满足目标、代码是否符合范围、实际输出是否满足验收。按风险决定是否需要独立或专项审查；不强制每个任务使用多个代理，审查也不能代替运行验证。

优先运行与改动相关的测试、静态检查、构建或实际流程检查。修复缺陷先复现或取得可靠证据，再验证修复；检查失败时定位和修正，保持原验收标准。已有无关失败要说明归属，不能据此宣称全部通过。根据用户实际结果查看页面、文件、响应或状态变化，不只看测试退出码。低风险文案或样式改动可直接核对结果，无须编造重复实现的测试。

交付时明确区分以下事实，不将前一项当作后一项的证据：

- **已编写**：完成了哪些文件或改动。
- **已测试**：实际运行的命令或操作、环境、结果及证据位置；模拟数据、桩和静态审查须标明。
- **已现场验证**：在明确环境中实际走通了哪些业务步骤；没有运行就写“未验证”，本地通过不代表生产通过。
- **已交付**：提供了什么、位于哪里、当前验收结论；交付文件不等于安装、发布或上线。

证据来自用户、其他代理或既有日志时，标注来源与局限，不称为自己实际执行；命令或结果缺失就说明缺失，不补造。列出未运行的检查及原因、已知问题和剩余风险，并给出下一步。关键验收未满足或证据不足时，明确报告部分完成或待验证，不宣称完整通过。不承诺零缺陷、绝对安全或全环境兼容。
